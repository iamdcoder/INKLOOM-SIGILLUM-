# UX Acceptance Criteria

| ID | Acceptance criterion | Evidence required |
|---|---|---|
| UX-001 | Creator can identify supported formats and required submission context before upload | Creator walkthrough |
| UX-002 | Creator can distinguish upload, parse, analysis and review states | State transition walkthrough |
| UX-003 | Reviewer can identify highest-risk unresolved issue without reading every finding | Risk-first workbench usability test |
| UX-004 | Every finding opens exact content location and source evidence | Finding-to-source navigation test |
| UX-005 | Evidence insufficiency is visibly distinct from low confidence and from contradiction | State comprehension test |
| UX-006 | Creator can compare, accept, edit or reject a correction and understand that acceptance creates a new version | Correction journey walkthrough |
| UX-007 | Reviewer can approve/reject/request changes only when backend state and permission allow it | Role/state negative tests |
| UX-008 | Brand Owner can inspect pack version, source, scope and validity before approval | Knowledge Pack walkthrough |
| UX-009 | Admin can manage roles/configuration without implicit content or approval privilege | Permission journey test |
| UX-010 | Critical tasks work at laptop width and by keyboard | Responsive + keyboard test |
| UX-011 | Loading, empty, error, denied, stale, parser warning, low OCR and outage states are designed | State catalogue review |
| UX-012 | Interface never implies approval for pending, failed, incomplete or unauthorised work | Negative-state test |

**Phase 01 gate:** UX design documents can be complete while actual interactive prototypes and accessibility validation remain pending. Do not pass the gate until prototypes and walkthrough evidence exist.
